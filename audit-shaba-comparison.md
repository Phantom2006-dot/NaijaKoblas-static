# ShabaAutos role and admin comparison audit

**Audit subject:** ShabaAutos role and admin comparison
**Compared systems:** `/home/ubuntu/workspace/ShabaAutos1/shabaautos` and `/home/ubuntu/workspace/NaijaKoblas-static`
**Audit date:** 2026-11-02
**Scope:** role structure, dashboards, tables, audit/logging, navigation, and upload workflows.
**Constraint:** ShabaAutos was inspected only; no ShabaAutos application code was changed.

## Executive summary

ShabaAutos is organized around a dealership operations control centre. Its authenticated roles are customer, staff, and admin; staff and admin share one operations route, with server-side authorization and selected admin-only actions. The dashboard is materially broader than NaijaKoblas’s current privileged UI: it presents an operations summary, inventory table, seller/concierge/import/rental/offer/inspection queues, analytics, notifications, settings, and an admin-only audit log.

NaijaKoblas has a more marketplace-native four-role model—customer, seller, staff, admin—with seller ownership and seller-specific fulfillment boundaries represented directly in the schema and tRPC procedures. Its authorization model is explicit and capability-oriented, and its product image upload path has stronger marketplace ownership checks, Cloudinary fail-closed behavior, rate limiting, concurrency limiting, content-signature checks, and cleanup. The trade-off is that staff/admin dashboards are split across separate routes and are narrower: staff primarily reviews seller records and creates seller drafts; admin manages account roles and pending Paystack reconciliation. There is no comparable unified operations table/queue, analytics workspace, settings editor, or visible audit-log screen in the inspected NaijaKoblas UI.

## Findings

### 1. Role structure and authorization

- **ShabaAutos uses three application roles:** `customer`, `staff`, and `admin`. The role is carried through the authenticated user model and enforced by `requireAuth`/`requireRole`; admin is treated as having access to staff/customer operations. The demo-mode branch also exposes customer/staff/admin personas. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server/middleware/auth.ts:3-4,89-171,243-286`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/components/Header.tsx:229-259`.
- **NaijaKoblas uses four database enum roles:** `customer`, `seller`, `staff`, and `admin`. The capability map distinguishes seller dashboard, seller review, staff management, and admin management; seller fulfillment is separately gated, including a deliberate suspended-seller fulfillment exception. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/drizzle/schema.ts:17-32,38-49`; `/home/ubuntu/workspace/NaijaKoblas-static/server/_core/authorization.ts:4-17,52-76`; `/home/ubuntu/workspace/NaijaKoblas-static/server/routers.ts:60-66,204-289`.
- **NaijaKoblas has the stronger domain separation for a marketplace.** Seller access is tied to the seller’s own account, approved application/store state, and product ownership. Staff/admin can act on seller-owned listings, but the seller retains publishing control. ShabaAutos instead centralizes operational work around staff/admin and does not have a first-class seller workspace role in the inspected application.
- **ShabaAutos has a stronger terms gate for all authenticated service access.** `requireAuth` blocks routes until terms are accepted except for the profile/sync/acceptance endpoints. NaijaKoblas’s inspected authorization focuses on Clerk identity, verified email, role procedures, and protected routes; the source does not show an equivalent global terms-acceptance gate. Source: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server/middleware/auth.ts:174-223`.

### 2. Dashboards and operational coverage

- **ShabaAutos has one unified Operations Dashboard route.** `App.tsx` mounts `OperationsDashboardScreen` at `operations-dashboard`, and the header exposes it to staff/admin as “Staff Workspace” or “Admin Operations.” Source: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/App.tsx:271-273`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/components/Header.tsx:229-236`.
- **ShabaAutos dashboard coverage is broad:** overview metrics, inventory, seller reviews, concierge, imports, rentals, offers, inspections, analytics, notifications, site settings, and an admin-only audit tab. The overview shows total inventory, awaiting approval, available, reserved, sold, and unread-alert counts. Source: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:333-352`.
- **ShabaAutos separates staff and admin powers inside the same dashboard:** staff can create/edit drafts and manage media; only admin can approve listings, permanently delete vehicles, change lifecycle status, edit settings, and view the audit tab. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:351-352,378-381`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server/routes/cms.ts:91-205`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server.ts:548-649,2411-2452`.
- **NaijaKoblas splits dashboards by role and route:** `/seller` for the seller workspace, `/staff` for seller oversight/intake, and `/admin` for admin access. `/account` is the customer account hub and links to the role-specific portal. Source: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/App.tsx:18-40`; `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:46-82,87-160`.
- **NaijaKoblas seller dashboard is appropriately ownership-scoped:** store profile, seller-owned products/inventory, draft-to-published lifecycle, primary-image requirement, and paid-order-line fulfillment. Suspended sellers retain a fulfillment-only view for already-paid orders. Source: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:134-160`; `/home/ubuntu/workspace/NaijaKoblas-static/server/routers.ts:204-289`.
- **NaijaKoblas staff dashboard is narrower than ShabaAutos:** it lists seller applications and permits approve/reject/suspend/re-approve, plus a separate staff product-intake panel for creating drafts for approved active sellers. Source: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:166-173`; `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/StaffProductIntakePanel.tsx:1-80`; `/home/ubuntu/workspace/NaijaKoblas-static/server/routers.ts:291-327`.
- **NaijaKoblas admin dashboard is focused on access and payment exceptions:** account-role listing with grant/revoke staff controls and paginated pending Paystack reconciliation. It does not expose a ShabaAutos-like inventory, seller queue, analytics, settings, notification inbox, or audit-log panel. Source: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:175-198`; `/home/ubuntu/workspace/NaijaKoblas-static/server/routers.ts:328-402`.

### 3. Tables, queues, and operational data presentation

- **ShabaAutos has a true operations inventory table** with vehicle, stock ID, price, lifecycle, approval, inspection, and actions columns. It supports search, lifecycle filtering, edit, admin approval, and admin deletion. Source: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:421-430`.
- **ShabaAutos models multiple operational queues** behind the dashboard (`sell`, `concierge`, `imports`, `rentals`, `offers`, `inspections`) and maps notifications to those queues. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:312-331`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/services/api.ts:1000-1015`.
- **NaijaKoblas data tables are role-specific list views rather than a unified operations table.** Seller products and seller order lines are shown as portal rows; staff sees seller application rows; admin sees users and pending payments. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:134-198`.
- **NaijaKoblas’s underlying relational model is strong for marketplace integrity:** seller applications, seller stores, seller products, product images, orders, order items, payment transactions, notifications, and account audit events are normalized with ownership/status indexes and constraints. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/drizzle/schema.ts:58-180,182-256`.
- **Recommendation implication:** do not copy ShabaAutos’s vehicle/inventory vocabulary into NaijaKoblas. Copy the operations pattern—queue-oriented tabs, server-backed counts, filters, empty/error states, and action-specific tables—using seller listings, orders, applications, fulfillment, and payment exceptions as the domains.

### 4. Audit and logging

- **ShabaAutos has an operator-visible audit log.** The admin-only `/api/ops/audit` endpoint returns recent audit entries, and the dashboard renders action, resource type/id, actor role, and timestamp. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server.ts:648-649`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:372`.
- **ShabaAutos records many CMS mutations:** draft creation, approval, listing updates, deletion, image upload/add/update/delete/reorder, settings changes, and API-key changes. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server.ts:610,626,1287-1289,2442-2448,2523`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server/routes/cms.ts:45,159,189,241,278,310,342`.
- **ShabaAutos also records measured activity analytics** for vehicle page views, detail views, and searches, and exposes an analytics workspace. Sources: `/home/ubuntu/workspace/ShabaAutos1/server.ts:82-117,261-299`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server.ts:2539-2543`; note that the first path above is the repository root alias in the source tree and the operative file is `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server.ts`.
- **NaijaKoblas persists an append-only account audit trail, but the inspected UI has no audit-log reader.** `accountAuditEvents` stores actor, target, event type, metadata, and timestamps; server transactions write events for admin bootstrap, seller applications/activation/status changes, staff access changes, staff-created drafts, staff image uploads, order creation, payment verification/failure, and fulfillment changes. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/drizzle/schema.ts:80-91`; `/home/ubuntu/workspace/NaijaKoblas-static/server/db.ts:130-160,235-259,459-568,681-712,820-828,1077-1085,1202-1281,1368-1382`.
- **NaijaKoblas notifications are better modeled as private, deduplicated business events** and have mark-read/mark-all-read procedures, but they are user notifications rather than an operator audit viewer. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/drizzle/schema.ts:93-109`; `/home/ubuntu/workspace/NaijaKoblas-static/server/routers.ts:74-79`.
- **Gap:** NaijaKoblas should add an admin-only, paginated audit reader with actor/target/event/time filters, plus an admin/staff operational activity view if the marketplace needs queue-level diagnostics. Do not expose raw metadata to ordinary customers.

### 5. Navigation and information architecture

- **ShabaAutos uses a single-screen state machine plus content routes.** `App.tsx` tracks `currentScreen`, translates screen IDs to paths, updates browser history, and renders views conditionally. Header, mobile bottom navigation, mobile sidebar, and account dropdown all feed the same navigation callback. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/App.tsx:32-79,114-154,187-319`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/components/Header.tsx:229-259`.
- **ShabaAutos keeps privileged navigation close to the authenticated account panel** and labels it by role. This is efficient for a single-application dealership console, but the dashboard itself then carries a horizontal/tabbed operations navigation for many queues. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/components/Header.tsx:229-236`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:333-352`.
- **NaijaKoblas uses explicit URL routes with wouter.** Public storefront routes are wrapped in `StoreShell`; `/admin` intentionally bypasses that shell, while `/seller` and `/staff` are dedicated routes. Source: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/App.tsx:16-44`.
- **NaijaKoblas’s route model is clearer for role-specific deep links and access-denied states.** The account page selects the correct portal link from the server-returned role and seller status; admin has a dedicated Clerk/server role gate. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:46-82`; `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AdminAccessPage.tsx` (admin entry and role verification); `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AuthPage.tsx` (role-aware post-login links).
- **Gap:** navigation is functionally complete for current NaijaKoblas roles, but staff/admin workflows are fragmented. A protected operations shell with a consistent sidebar/tab bar would improve discoverability without collapsing seller/customer boundaries.

### 6. Upload workflows and media administration

- **ShabaAutos supports staff/admin vehicle media management.** Uploads are allowed after a vehicle draft/listing exists, use up to 10 images per request and 8 MB per file, validate JPEG/PNG/WebP MIME plus magic bytes, store locally or in Cloudinary, and support per-image primary, caption, delete, and reorder operations. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server/storage.ts:9-27,83-103,114-168`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/server/routes/cms.ts:29-45,206-359`; `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:189-244,381-430`.
- **ShabaAutos’s workflow intentionally saves the database draft before binary upload.** If upload fails, the draft remains and the UI keeps selected files available for retry. Source: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:224-244`.
- **NaijaKoblas product uploads are more tightly scoped to marketplace ownership.** The upload route requires a verified marketplace user, validates a strict `prod_` identifier, loads the product/seller target, permits only the seller owner or staff/admin for an approved active seller, requires Cloudinary, enforces one active upload, 12 requests per user per ten minutes, 1–4 files per batch, 8 MB each/32 MB total, MIME and magic-byte validation, trusted HTTPS Cloudinary URLs, and cleanup on persistence failure. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/server/uploads/routes.ts:24-70,72-120,123-180,201-243,246-331`; `/home/ubuntu/workspace/NaijaKoblas-static/server/commerce/product-upload.ts:24-57`.
- **NaijaKoblas stores richer product-image metadata** including public ID, asset ID, dimensions, caption, display order, primary flag, creator, and product ownership; it limits a listing to 10 images and requires a primary image before publishing. Sources: `/home/ubuntu/workspace/NaijaKoblas-static/drizzle/schema.ts:158-180`; `/home/ubuntu/workspace/NaijaKoblas-static/server/db.ts:790-850`; `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/AccountPages.tsx:138-140`.
- **Upload UX differs by audience:** ShabaAutos offers one operations image manager embedded in the vehicle editor; NaijaKoblas has seller-owned photo panels and also permits staff/admin to upload to seller drafts, with notifications when staff changes a seller listing. Sources: `/home/ubuntu/workspace/ShabaAutos1/shabaautos/src/views/OperationsDashboardScreen.tsx:375-430`; `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/SellerProductPhotosPanel.tsx:1-20`; `/home/ubuntu/workspace/NaijaKoblas-static/client/src/pages/StaffProductIntakePanel.tsx:1-80`.

## Recommendations for NaijaKoblas

1. **Add a protected operations shell rather than merging roles.** Keep `/seller`, `/staff`, and `/admin` route boundaries, but give `/staff` and `/admin` a shared operations layout with a stable sidebar or tab bar. Suggested sections: Overview, Seller review, Catalog/listings, Orders/fulfillment exceptions, Payments, Notifications, and Audit. This adopts ShabaAutos’s discoverability without weakening NaijaKoblas’s role separation.
2. **Introduce server-backed operations summary metrics.** Add role-scoped counts such as pending seller reviews, active sellers, draft/published/low-stock listings, pending payments, paid orders awaiting fulfillment, and unread staff notifications. Render these as cards with explicit loading, empty, and error states, following the ShabaAutos overview pattern.
3. **Build a catalog/listings table for staff/admin.** Include seller, product, status, stock, price, primary-image readiness, updated time, and actions. Preserve seller ownership: staff may prepare/edit drafts only where policy allows, while publishing should remain seller-owned unless an explicit admin procedure is added and audited.
4. **Expose the existing audit trail to administrators.** Add a paginated `admin.auditEvents` procedure backed by `accountAuditEvents`, with filters for event type, actor, target, and date range. Add an admin-only table showing event, actor, target, metadata summary, and timestamp. The audit trail already exists; the missing layer is controlled retrieval and presentation.
5. **Add a staff/admin notification inbox or queue links.** Reuse `userNotifications` and its deduplication model, but add operational links to seller review, listing intake, payment exceptions, and fulfillment exceptions. Provide mark-read and mark-all-read actions in the operations shell.
6. **Add admin payment and order exception tables beyond pending reconciliation.** ShabaAutos demonstrates queue-oriented workflow tabs; NaijaKoblas should extend the existing admin payment view to include failed/mismatched/manual-review cases and a staff-facing paid-but-unfulfilled queue, with all state transitions audited.
7. **Retain NaijaKoblas’s upload security baseline.** Do not replace the current verified-user, seller-ownership, Cloudinary-only, content-signature, rate-limit, concurrency, URL-validation, and cleanup controls with a simpler ShabaAutos-style generic upload route. If adding staff/admin bulk upload, reuse the same `canUploadProductImages`/storage contract and record actor/target audit events.
8. **Improve media management parity carefully.** Add captions, delete, reorder, and possibly per-image replacement if business needs require it; preserve the current primary-image uniqueness and publish gate. Add staff/admin UI feedback when a staff-uploaded image is awaiting seller review.
9. **Use a consistent dashboard table component.** ShabaAutos’s inventory table makes lifecycle/approval/inspection distinctions explicit. NaijaKoblas should similarly make product status, seller approval/store status, stock, payment state, and fulfillment state visibly independent rather than relying on generic portal rows.
10. **Keep route-level access-denied and role verification.** NaijaKoblas’s explicit route model is a strength for deep linking and security messaging. Any operations shell should still use server-derived role procedures; never trust client role state for authorization.
11. **Add operational analytics only when tied to recorded events.** ShabaAutos’s documented analytics approach is measured-data-only. For NaijaKoblas, start with catalog views, checkout starts, payment outcomes, seller listing events, and fulfillment transitions; store only the minimum necessary data and label inferred metrics clearly.
12. **Document the role matrix and action matrix.** Create a concise matrix covering customer, seller, staff, and admin for account access, seller review, product create/edit/publish, image upload/delete, order fulfillment, payment reconciliation, settings, notifications, and audit read access. Use the server procedures as the source of truth.
