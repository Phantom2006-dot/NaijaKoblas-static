# Seller dashboard and product workflow audit

**Scope:** seller activation, store profile, product creation, image upload, publish gating, inventory, and order fulfilment. **Audit date:** 2026-11-02. **Project:** `/home/ubuntu/workspace/NaijaKoblas-static`.

## Executive summary

The implementation has a sound server-side ownership model: seller procedures are authenticated and require an approved seller application; product rows are owned by `sellerUserId`; upload authorization checks the target listing and seller; public catalog reads only published, in-stock products from active stores; checkout revalidates price, status, size, store activity, and stock in a transaction; and fulfilment mutations scope the order item to the acting seller. Focused tests pass: 21 tests across activation, upload validation, fulfilment transitions, and authorization.

The main gaps are workflow coherence and seller completeness. Inactive-store and suspended states are represented differently across the UI and backend, seller creation remains enabled while a store is inactive, publication gives no consolidated readiness checklist, and several essential seller capabilities are absent (editing core listing fields after creation, deleting/removing/reordering media, inventory history/low-stock visibility, and operational fulfilment features). The current one-click activation also auto-approves legacy pending applications, which is intentional in code but creates a confusing coexistence with the staff review portal and application schema.

## Findings

1. **High — Seller activation bypasses the apparent staff-review workflow for pending applications.** `account.becomeSeller` calls `activateSellerAccount` ([`server/routers.ts:96-105`](server/routers.ts#L96-L105)); when an application is `pending`, the database transaction changes it to `approved`, records a self-service note, and creates the seller store ([`server/db.ts:322-368`](server/db.ts#L322-L368)). The staff UI still presents pending applications with Approve/Decline controls ([`client/src/pages/AccountPages.tsx:165-171`](client/src/pages/AccountPages.tsx#L165-L171)), and the schema retains legal name, phone, craft summary, review note, reviewer, and reviewed-at fields ([`drizzle/schema.ts:58-78`](drizzle/schema.ts#L58-L78)). This is a policy/product ambiguity: a seller can approve themselves while staff sees a record described as reviewable. **Impact:** staff may believe approval is required, while a pending applicant receives a conflicting experience and audit history. The behavior is secure if direct activation is intended, but the governance model is unclear.

2. **High — Inactive-store state is not a coherent lock across seller capabilities.** `sellerProcedure` requires role plus an approved application, but does not check `sellerStores.isActive` ([`server/_core/trpc.ts:31-39`](server/_core/trpc.ts#L31-L39)). Consequently an approved seller with an inactive store can load the dashboard and call `createProduct`, whose database function checks no store/activity state ([`server/db.ts:643-661`](server/db.ts#L643-L661)). The UI explicitly says the store is “Not active” and support is required, but still renders the create form ([`client/src/pages/AccountPages.tsx:134-138`](client/src/pages/AccountPages.tsx#L134-L138)). By contrast, profile update rejects inactive stores ([`server/db.ts:410-419`](server/db.ts#L410-L419)), image upload rejects inactive stores ([`server/db.ts:774-781`](server/db.ts#L774-L781)), and publish rejects inactive stores ([`server/db.ts:891-897`](server/db.ts#L891-L897)). **Impact:** sellers can create drafts that they cannot complete, upload, or publish, producing a dead-end and inconsistent authorization boundary.

3. **Medium — The publish gate is technically enforced but poorly surfaced as a workflow.** The server requires active store, stock >= 1, and a selected primary image ([`server/db.ts:891-905`](server/db.ts#L891-L905)). The client disables Publish when stock, store activity, or primary image is missing and displays only an image hint in that case ([`client/src/pages/AccountPages.tsx:138-138`](client/src/pages/AccountPages.tsx#L138-L138)). There is no explicit readiness checklist for description/category/price/sizes because those are required at creation, no publish error summary, and no direct “add photos” action from the listing row. **Impact:** a seller sees a disabled button with no reason when stock is zero or store inactive; the separate photo section is below the dashboard, so the next action is not obvious. Publish errors from the server are shown only in the generic bottom error area ([`client/src/pages/AccountPages.tsx:145-145`](client/src/pages/AccountPages.tsx#L145-L145)).

4. **Medium — Product editing is incomplete after creation.** The create form collects name, description, category, price, sizes, and inventory ([`client/src/pages/AccountPages.tsx:137-137`](client/src/pages/AccountPages.tsx#L137-L137)), but the only seller edit form exposes price and stock ([`client/src/pages/AccountPages.tsx:138-138`](client/src/pages/AccountPages.tsx#L138-L138)). The API technically accepts partial changes to all seller product fields ([`server/routers.ts:231-249`](server/routers.ts#L231-L249)), but no UI invokes changes to name, description, category, or sizes. **Impact:** sellers cannot correct title/content/category/variant data without staff intervention or an unsupported API call; this is a missing core capability, especially before or after publishing.

5. **Medium — Image management is upload-and-primary only; there is no removal, replacement, reorder, caption editing, or retry/resume workflow.** The schema stores caption and display order ([`drizzle/schema.ts:158-180`](drizzle/schema.ts#L158-L180)), but the seller API exposes only `setPrimaryImage` ([`server/routers.ts:252-259`](server/routers.ts#L252-L259)); the uploader exposes upload and “Make primary” only ([`client/src/components/store/ProductImageUploader.tsx:118-134`](client/src/components/store/ProductImageUploader.tsx#L118-L134)). Images are appended in upload order and the first image is automatically primary ([`server/db.ts:790-817`](server/db.ts#L790-L817)). **Impact:** an incorrect or obsolete image cannot be removed, and sellers cannot control gallery order or accessibility captions even though the data model anticipates those fields. A failed batch is all-or-nothing from the database perspective, but the seller must manually retry the whole batch.

6. **Medium — Image upload authorization is stronger than the UI state model, causing confusing inactive-store failures.** Upload routes require verified auth, validate the product ID, load seller ownership, require approved seller plus active store, and validate MIME plus file signatures ([`server/uploads/routes.ts:54-113`](server/uploads/routes.ts#L54-L113), [`server/uploads/routes.ts:246-329`](server/uploads/routes.ts#L246-L329)). However `SellerProductPhotosPanel` renders upload controls for every product returned by the approved-application dashboard and always passes `canSetPrimary` ([`client/src/pages/SellerProductPhotosPanel.tsx:5-15`](client/src/pages/SellerProductPhotosPanel.tsx#L5-L15)). For an inactive store, the controls appear usable and only fail after a network request. **Impact:** the seller is not told upfront that uploads are blocked, and the primary-image mutation can remain available independently of upload/store state because `setSellerProductPrimaryImage` checks product ownership but not store activity ([`server/db.ts:839-862`](server/db.ts#L839-L862)).

7. **Medium — Inventory is a single mutable count with no seller-facing reservation, adjustment, or low-stock model.** The schema stores only `inventoryCount` on the product ([`drizzle/schema.ts:137-156`](drizzle/schema.ts#L137-L156)). Checkout decrements it transactionally before payment and pending-payment orders reserve stock ([`server/db.ts:952-1003`](server/db.ts#L952-L1003)); seller stock edits are blocked while any pending reservation exists ([`server/db.ts:879-889`](server/db.ts#L879-L889)). The UI displays “in stock” and allows direct replacement of the count, but gives no reserved/available breakdown, low-stock threshold, adjustment reason, history, or indication that a pending checkout is preventing edits ([`client/src/pages/AccountPages.tsx:138-138`](client/src/pages/AccountPages.tsx#L138-L138)). **Impact:** sellers cannot explain stock changes, identify reserved units, or proactively manage replenishment; a blocked save is surprising without a reservation-aware explanation.

8. **Medium — Fulfilment is line-level and state-safe but operationally minimal.** Server-side ownership, paid-order gating, allowed transitions, and order roll-up are implemented ([`server/db.ts:1291-1389`](server/db.ts#L1291-L1389); [`server/commerce/fulfillment.ts:5-21`](server/commerce/fulfillment.ts#L5-L21)). The UI provides one next-state button and optional carrier/tracking inputs for each line ([`client/src/pages/AccountPages.tsx:140-145`](client/src/pages/AccountPages.tsx#L140-L145)). Missing capabilities include fulfilment filtering/search/pagination beyond a hard limit of 200 rows, bulk actions, required/validated tracking at shipment, cancellation/exception/return handling, pickup/delivery confirmation, and a seller-facing order detail view. **Impact:** small volumes work, but merchants cannot efficiently operate a growing order queue or model common delivery exceptions. The optional tracking fields also allow “shipped” without shipment evidence.

9. **Low — Seller dashboard data is duplicated and can become visually inconsistent.** `/seller` mounts `SellerDashboardPage` and then a second `seller.dashboard` query through `SellerProductPhotosPanel` ([`client/src/pages/SellerWorkspacePage.tsx:1-6`](client/src/pages/SellerWorkspacePage.tsx#L1-L6); [`client/src/pages/SellerProductPhotosPanel.tsx:5-15`](client/src/pages/SellerProductPhotosPanel.tsx#L5-L15)). Mutations in the dashboard invalidate/refetch only the first query instance, while the photo panel separately refetches after upload/primary changes. **Impact:** after product edits, the photo section may lag until its independent query refreshes, and the page performs duplicate dashboard requests; this contributes to confusing status presentation during rapid edits.

10. **Low — Store profile is editable but has no seller preview or product attribution controls.** The profile form exposes display name, city, and optional description ([`client/src/pages/AccountPages.tsx:136-136`](client/src/pages/AccountPages.tsx#L136-L136)); the public catalog exposes seller display name and city but not store description or a seller storefront route ([`server/db.ts:918-942`](server/db.ts#L918-L942)). **Impact:** sellers cannot verify how their public identity appears, and shoppers cannot browse a seller’s full collection or read the supplied store description. This makes profile completion feel disconnected from marketplace outcomes.

## Recommendations

1. Decide and document one activation policy. If self-service activation is intentional, retire or relabel the pending-review workflow, stop presenting pending applications as awaiting staff approval, and make the audit event and staff dashboard explicitly say “self-activated.” If review is required, do not convert `pending` to `approved` inside `becomeSeller`.
2. Introduce one server-side seller-state guard used consistently by dashboard reads and mutations: approved application, seller role, existing active store. Either fully block inactive sellers (including product creation and primary-image updates) or expose a deliberate read-only recovery mode with disabled controls and clear support messaging.
3. Add a per-listing readiness model/checklist (active store, valid price/content, at least one image, primary image, positive available stock) and return structured blockers from the API. Render blockers next to the listing and make each blocker actionable, rather than relying on a disabled Publish button and a generic page-level error.
4. Build a complete product editor using the already-supported partial update input: name, description, category, sizes, price, and inventory. Clarify whether edits to published listings are immediate or require re-review, and preserve audit history for material changes.
5. Add image lifecycle mutations for delete, reorder, caption, and replace, with protection against deleting the final primary image of a published listing. Disable or hide upload/primary controls when the store is inactive and show server limits/errors before submission.
6. Replace raw stock replacement with inventory operations or at minimum show `on hand`, `reserved`, and `available`, plus low-stock thresholds and a reason/history feed. Explain the pending-payment reservation lock directly beside the stock form.
7. Extend fulfilment with order filters, pagination/cursors, seller order detail, bulk processing, required carrier/tracking validation at the shipped transition (or an explicit “tracking unavailable” reason), and exception/return/cancellation states. Keep all transitions server-enforced.
8. Share/invalidate one seller dashboard query between the main dashboard and photo panel, or fold media into the listing card. This removes duplicate requests and prevents stale gallery/status sections.
9. Add a seller preview/storefront route showing display name, city, description, published products, stock availability, and gallery images. This gives sellers a clear completion target and improves customer attribution.
10. Add integration tests around the missing state boundaries: inactive store cannot create/edit/upload/publish; suspended seller can only fulfil paid historical orders; pending application activation matches the chosen policy; every product edit is ownership-scoped; and image deletion cannot orphan a published listing without a primary image.
