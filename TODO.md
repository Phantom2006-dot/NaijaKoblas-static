# NaijaKoblas TODO

## Implemented in the current worktree

- Clerk remains the sole end-user identity provider. The browser uses Clerk email/password sign-in/sign-up and sends session Bearer tokens to tRPC. The server validates a paired key configuration, exact HTTPS `APP_BASE_URL` origin and the authoritative verified primary email; Neon remains the source of customer/seller/staff/admin roles.
- `/admin` is a separate headless entry outside the public storefront shell. Its Clerk session is checked against the Neon role; only `admin` can open admin procedures/data. No admin link was added to public navigation; the private admin toolbar includes notifications, return-to-store and sign-out.
- A seller uses the same account for shopping and an approved seller workspace; signed-in navigation exposes Seller Workspace/Staff Portal according to the DB role, and `/account` links into the workspace. Sellers can return to customer account functions. The server remains the role/ownership boundary.
- Seller/staff/admin product-photo upload is implemented. Sellers upload only to their own listings; staff/admin can create a draft for an approved seller with an active store and upload photos. Drafts stay unpublished until the seller adds/selects a primary image and then publishes. Available stock and a selected primary gallery image are enforced in the server transaction as well as the client button.
- Uploads are authenticated, memory-bounded and use Cloudinary only: JPEG/PNG/WebP, server-side magic-byte checks, max 8 MB per file, max 4 images/32 MB per batch and max 10 images per listing. The route authorizes the product before parsing, limits one active batch per process and 12 batches per account per 10-minute process-local window, bounds multipart fields/parts, and rejects oversized declared bodies. The slot is released only after Multer drains parser cleanup or after Cloudinary, DB persistence and any compensation finish; it is never freed early on response close. New listing mutations do not accept arbitrary external image URLs; migration-only legacy HTTPS images are stored as explicit format `external`.
- Cloudinary public ID/asset ID/format/dimensions/order/primary state are stored in Neon, the public product page renders galleries, and sellers can select a primary photo. Failed metadata persistence triggers up to three Cloudinary delete attempts and logs if compensation still fails; no durable orphan-asset reconciler is implemented.
- Recipient-owned in-app notifications cover seller application receipt/review queues/outcomes, staff access changes, staff-created drafts/photos, verified payment success/failure and per-line fulfillment. Application/review/role notifications commit atomically with their state changes. Event keys are idempotent and long keys use a digest; links are safe local paths. The bell supports polling/read/mark-all and keyboard dismissal/focus return. No email/SMS/push channel or delivery worker is implemented.
- Public keyboard controls have visible focus indicators. The mobile main-nav disclosure traps Tab/Shift+Tab while open, handles Escape/outside dismissal and returns focus; the full-screen mobile filter drawer has dialog semantics, scroll lock, focus containment, Escape/backdrop/Apply close and focus return.
- PostgreSQL migration `0001_married_dagger.sql` adds product galleries and recipient-scoped notifications with a legacy-primary-image backfill; `0002_aspiring_iceman.sql` adds an explicit format constraint including the legacy-only `external` value. Fly `release_command` applies migrations before the API release starts, preferring `DATABASE_URL_UNPOOLED`.

## Validation and remaining risks

- Passed on the current worktree: `pnpm check`; `pnpm test` (15 files/69 tests); `pnpm build`; `pnpm build:static`; `git diff --check`; strict Fly configuration validation; Linux/AMD64 Fly image build (about 75 MB); compiled production-server health/auth-status smoke test on the native host; all three PostgreSQL migrations applied twice to an ephemeral local PostgreSQL database, recording exactly three migrations and the image-format check.
- Independent backend security/migration and frontend accessibility audits found no remaining medium/high issues. The final UI audit verified Tab/Shift+Tab containment for both menu and filter, Escape/outside close and focus return, photo-required publishing, and `/admin` isolation. On filter viewport resize to desktop, focus intentionally moves to the first visible desktop filter control.
- The ARM64 sandbox could not execute the AMD64 Node image under QEMU. A real Fly release, pre-release migration, healthy machine check and Vercel build are still required before claiming this code is live.
- The upload route intentionally returns 503 until all three `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` values are added through Fly protected Secrets. No real upload, seller ownership rejection, cleanup failure or gallery publish flow has been tested against Cloudinary.
- The current worktree is uncommitted. The ShabaAutos source audit was read-only; its demo-token/role-metadata fallbacks, local ephemeral storage, orphan upload path and arbitrary remote image URL acceptance were deliberately not copied.
- Core application state notifications are transactional, but there is no multi-channel delivery queue or durable retry worker for any external notification channel. Cloudinary cleanup has bounded retries/logging but no scheduled orphan reconciler. The upload limiter is process-local and must become shared if the app is scaled beyond its current one-machine model. A hung Cloudinary operation can hold the single-process upload slot until it settles.
