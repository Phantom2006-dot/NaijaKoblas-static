# Audit: Customer navigation and homepage flow

**Scope:** public homepage, global navbar, login state, customer account, vendor entry points, route manifests, and seller-facing navigation behavior.

**Repository:** `/home/ubuntu/workspace/NaijaKoblas-static`

**Audit status:** Source-only audit. No application code was changed.

## Summary

The public storefront has a coherent customer-to-account flow, and the server/database role model is authoritative (`customer`, `seller`, `staff`, `admin`). The main navigation defect is client-side: `Navbar` always adds `Become a Vendor` and `Get Started`, then appends `Seller Workspace` for a seller. Therefore an active signed-in seller sees seller workspace plus customer acquisition CTAs that no longer apply. The footer also always exposes `Become a Vendor`, and the homepage can expose a `Become a Seller` CTA when the catalog is empty. The vendor page itself correctly changes its activation panel for active sellers, but that role-aware behavior is not propagated to the global shell or all homepage/footer entry points.

There is also a transient auth-state problem: `useAuth` reports `isAuthenticated` only after both Clerk and `auth.me` resolve, while `Navbar` renders immediately. A signed-in seller can briefly see `Sign In`/generic account affordances before the database account query completes. The route manifests are inconsistent: the root manifest omits `/account`, `/seller`, `/staff`, and `/admin`, while the client and built manifests include them; all manifests omit the implemented `/seller-fulfillment` route. This creates an incomplete route inventory for navigation tooling and QA.

## Findings

1. **Active sellers always receive irrelevant global seller-acquisition links.** `Navbar` initializes `links` with `Become a Vendor` (`/vendor`) and `Get Started` (`/waitlist`) for every auth state, then appends `Seller Workspace` only when `auth.user?.role === "seller"` (`client/src/components/store/StoreShell.tsx:74-84`). An active seller therefore sees `Become a Vendor`, `Get Started`, `Seller Workspace`, and `Account` simultaneously. This is the direct cause of the reported behavior. The seller role is available from `trpc.auth.me` and is server-derived (`client/src/_core/hooks/useAuth.ts:17-32`; `server/routers.ts:68-72`).

2. **The seller-specific check is too coarse for role-aware navigation.** The shell adds `/seller` for any user whose role is `seller` (`StoreShell.tsx:82`), but the account/vendor UI defines an active seller more narrowly as role `seller` plus an `approved` seller record and no moderation block (`client/src/pages/AccountPages.tsx:46-59`; `client/src/pages/StorePages.tsx:316-320`). A role-aware nav policy should use the same effective capability/status used by the account page, not role alone, so incomplete, suspended, or legacy seller records do not receive a misleading workspace destination. Server access is also more restrictive: `seller.dashboard` uses `sellerProcedure` (`server/routers.ts:204-213`), and authorization capabilities distinguish customers (`seller:apply`) from sellers (`seller:dashboard`) (`server/_core/authorization.ts:12-17`).

3. **The footer duplicates the vendor CTA unconditionally.** The Company footer column always renders `Become a Vendor` (`client/src/components/store/StoreShell.tsx:115-119`). Even after the header is corrected, signed-in active sellers will still encounter a seller-acquisition CTA on every storefront page. Footer behavior must use the same role-aware policy as the navbar, or replace the link for sellers with `Seller Workspace`/`Account`.

4. **Homepage vendor entry points are not role-aware.** The empty-catalog state renders `Become a Seller` linking to `/vendor` (`client/src/pages/StorePages.tsx:20-29`, specifically the catalog branch at line 26). The About page also always renders `Become a Seller` (`StorePages.tsx:266`). These are public acquisition surfaces and are reasonable for anonymous/customers, but active sellers should see `Open seller workspace` (or no seller CTA) instead. The homepage hero itself is customer-oriented (`Shop Collection`, `Our Story`) and does not have a seller CTA (`StorePages.tsx:20-25`), so the empty-state and footer are the relevant homepage-flow cases.

5. **`/vendor` has correct local role-aware content, but the global route remains discoverable to active sellers.** `SellerActivationPanel` distinguishes anonymous users, trusted staff/admin, blocked seller records, active sellers, and ordinary customers (`client/src/pages/StorePages.tsx:302-357`). For an active seller it says the seller space is ready and presents a `BecomeSellerButton`, which becomes `Open seller workspace` when role is `seller` and application status is `approved` (`client/src/components/store/BecomeSellerButton.tsx:23-42`). This means the page-level behavior is mostly correct; the issue is that the shell/footer still advertise `/vendor` as if the user were a prospect. The vendor hero copy and anchor CTA are also written as acquisition copy for every visitor (`StorePages.tsx:271-286`), so an active seller who deliberately visits `/vendor` sees redundant “Start Selling / Become a Seller” messaging before reaching the role-aware panel.

6. **`Get Started` points to a generic waitlist/early-access marketing route, not an authenticated customer action.** The nav maps `Get Started` to `/waitlist` (`StoreShell.tsx:79-80`), and `/waitlist` is a public route in `App.tsx:30`. The waitlist page is a newsletter/early-access experience, including “Free to join. First access when we launch.” (`client/src/pages/StorePages.tsx`, `WaitlistPage` implementation; related route at `App.tsx:30`). For an active seller this is especially confusing because their seller workspace is already active. For a signed-in customer, `Get Started` is also ambiguous: it does not lead to account setup, shopping, or seller activation. Rename it to an explicit marketing label (for example `Join the Waitlist`) or remove it from authenticated navigation.

7. **The account destination is exposed even when anonymous, while auth readiness is asynchronous.** The header action area always renders `Account` and `/account` (`StoreShell.tsx:91-98`), even when the preceding primary link is `Sign In`. `/account` is protected by `trpc.account.me`; unauthenticated access falls back to `AccessDenied` (`client/src/pages/AccountPages.tsx:39-45`), and the global tRPC error subscriber may redirect unauthorized requests to login (`client/src/main.tsx:17-30`). This works functionally but gives anonymous users a route that immediately becomes a sign-in flow rather than a clear `Sign In` affordance. More importantly, `useAuth` sets `isAuthenticated` only when Clerk is signed in *and* `auth.me` has returned (`useAuth.ts:17-32`), so the navbar can briefly show anonymous links or `Sign In` while a seller session is resolving. The shell should render a loading/neutral state until auth is resolved, then select the role-aware nav.

8. **Customer account behavior is otherwise aligned with the stated dual-use identity model.** `/account` loads private account data and orders only after the account query is available (`AccountPages.tsx:39-45`); active sellers receive an explicit seller dashboard callout (`AccountPages.tsx:49-50, 74-81`) and can switch back to shopping (`AccountPages.tsx:78`). The same identity model is reflected in the server (`server/routers.ts:85-105`) and schema (`drizzle/schema.ts:17-18, 38-49, 125-135`). The recommended fix should preserve this one-account model rather than hiding customer account/order access from sellers.

9. **Seller route access is server-protected, but client route declarations are not a complete manifest.** `App.tsx` implements `/account`, `/seller-fulfillment`, `/seller`, `/staff`, and `/admin` (`client/src/App.tsx:18-40`). The root `manus-routes.json` lists only public routes through `/404` and omits all private workspace routes (`manus-routes.json:1`). `client/public/manus-routes.json` adds `/account`, `/seller`, `/staff`, and `/admin` but still omits `/seller-fulfillment` (`client/public/manus-routes.json:1`); the built copy has the same omission (`dist/public/manus-routes.json:1`). This is route-inventory drift, not an authorization bypass: seller/admin procedures remain role-protected on the server (`server/routers.ts:204-213`; `server/_core/authorization.ts:56-71`).

10. **The route manifest title itself is inconsistent with UI terminology.** The manifests title `/vendor` as `Become a Vendor`, while the page and CTA predominantly say `Become a Seller` (`manus-routes.json:1`; `StorePages.tsx:282, 299, 351`). Choose one canonical term in navigation and metadata. Given the database/server naming (`seller`, `sellerApplication`, `sellerWorkspace`), `Seller` is the more internally consistent term.

## Exact recommended role-aware navigation behavior

Use one shared navigation policy derived from resolved `auth.me` plus the seller application record (or an equivalent server-returned effective capability), and reuse it in the header, footer, homepage CTA, and vendor page. Do not independently infer state from Clerk alone or from `role === "seller"` alone.

- **Anonymous / auth not configured / auth still resolving:** Show public shopping links (`Home`, `Products`, `Why Koblas`, `Contact Us`), a clearly labeled `Sign In`, and optionally `Join the Waitlist` if the marketing campaign is still active. Do not show `Account` as though it were already available. While auth is resolving, avoid flashing the anonymous menu over a known signed-in session; use a neutral/loading account affordance.
- **Authenticated customer:** Show `Account`, `Shop`/`Products`, cart, and a single explicit seller acquisition action such as `Become a Seller` linking to `/vendor` (or to `/account` if activation is intended to be account-first). `Get Started` should not remain an ambiguous second acquisition CTA; rename it to `Join the Waitlist` or remove it.
- **Active seller:** Replace `Become a Vendor`/`Become a Seller` with `Seller Workspace` linking to `/seller`; replace `Get Started` with either `Account`/`Orders` or remove it. Keep `Account` because sellers retain customer shopping and private order history. In the footer, replace `Become a Vendor` with `Seller Workspace` (and optionally keep `Account`). The homepage empty-catalog CTA should say `Open Seller Workspace` for this state.
- **Seller role with `pending`, `rejected`, `suspended`, incomplete, or inactive-store state:** Do not advertise seller activation as if it were available. Show `Account` plus a status-specific `Seller access`/`Contact support` destination. For suspended sellers, expose only the existing fulfillment-only entry point when the application status permits it (`/seller-fulfillment`); do not expose the full `/seller` workspace. The server’s capability and fulfillment rules remain authoritative (`server/_core/authorization.ts:43-54`).
- **Staff:** Show `Staff Portal` (`/staff`) and `Account`; do not show seller self-service CTAs. The existing UI correctly states that staff/admin roles cannot be changed through seller self-service (`BecomeSellerButton.tsx:36-38`).
- **Admin:** Show `Admin Portal` (`/admin`) and `Account`; keep `/admin` outside the storefront shell as currently implemented (`client/src/App.tsx:40`). Do not surface admin in public marketing navigation.

## Recommended implementation sequence (no code applied in this audit)

1. Create a single role/navigation selector that returns `customer`, `active seller`, `seller-restricted`, `staff`, `admin`, `anonymous`, or `loading` from the resolved backend account payload. Prefer returning the seller application/store status from one query so the shell does not make a second inconsistent decision.
2. Refactor `Navbar` and `Footer` to consume that selector. Remove unconditional `Become a Vendor` and `Get Started` entries for active sellers; replace them with `Seller Workspace` and customer account/order access. Use `Join the Waitlist` if `/waitlist` is intentionally retained.
3. Apply the same selector to homepage empty-catalog and About-page seller CTAs. At minimum, active sellers should receive `Open Seller Workspace`; restricted/incomplete sellers should receive a support/status message rather than a mutation CTA.
4. Keep `/vendor` publicly reachable for discovery, but make its hero/anchor copy state-aware for authenticated users and provide a prominent `Open Seller Workspace` action for active sellers. Do not rely on hiding links for security; retain server-side authorization.
5. Make the anonymous header action conditional (`Sign In` vs `Account`) and suppress or neutralize account/nav labels during the Clerk + `auth.me` loading window to prevent the seller flash.
6. Reconcile manifests: decide whether private routes belong in the canonical route manifest, then make root, client-public, and built outputs consistent. At minimum add `/seller-fulfillment`; if private routes are intentionally represented, include `/account`, `/seller`, `/seller-fulfillment`, `/staff`, and `/admin` consistently with explicit protected/private metadata if the manifest format allows it. Align `/vendor` title with chosen `Seller` terminology.
7. Add navigation tests for anonymous, customer, active seller, suspended seller, staff, and admin states, asserting both header and footer labels/targets and ensuring active sellers never see `Become a Vendor` or `Get Started`.
